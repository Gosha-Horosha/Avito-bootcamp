# Candidate Generation для поиска услуг Avito

Для каждого запроса из `benchmark_queries.parquet` возвращается 50 `item_id` из `benchmark_items.parquet`.
Метрика — Recall@50. Решение работает полностью локально, внешние API не используются.

## Результат (офлайн-валидация)

| Валидация | Recall@50 | Recall@100 | Recall@200 | Потолок пула |
|---|---|---|---|---|
| Сплит по тексту запроса, 1 инстанс на текст (7 453 запроса) | 0.8325 | 0.8747 | 0.9073 | 0.9416 |
| Сплит по полной комбинации `search_*`, перевзвешено под бенчмарк (37% знакомых текстов, 15 839 запросов) | 0.8359 | 0.8764 | 0.9084 | 0.9416 |

Финальные веса (`configs/weights.json`) подобраны на второй валидации: она ближе к составу бенчмарка.
Переобучение подбора весов проверено 2-fold: подбор на половине запросов → 0.8290 / 0.8401 на отложенной
половине (в среднем 0.8346 против 0.8359 in-sample). Разброс между половинами (±0.005) — реальная точность
офлайн-оценки; улучшения меньше ~0.005 стоит считать шумом.

## Подход

Одна стадия: несколько каналов поиска → общий пул кандидатов с точными скорами всех каналов → линейная смесь.

### Каналы

| Канал | Что сравнивается | Recall@50 канала + буст локации |
|---|---|---|
| `bm` | BM25 (k1=1.2, b=0.75): леммы запроса ↔ леммы «заголовок + описание + вид/тип услуги» | 0.743 |
| `e5` | `multilingual-e5-base`: `query: <запрос>` ↔ `passage: <заголовок>. <вид/тип услуги>` | 0.654 |
| `tc` | TF-IDF char_wb 3–5 по заголовку (словоформы, опечатки) | 0.605 |
| `tw` | TF-IDF по леммам заголовка, uni+bigram | 0.573 |
| `mc` | P(микрокатегория объявления \| запрос) по 30 ближайшим train-запросам | 0.522 |
| `hx` | средний e5 объявлений, кликнутых по похожим train-запросам | 0.503 |
| `sp` | TF-IDF «Вид/Тип услуги» из фильтров запроса ↔ те же поля объявления | 0.265 |

Лемматизация — `pymorphy2`. Из `item_infm_params_text` берутся только значения «Вид услуги» и «Тип услуги»:
остальное (график работы, цены, адрес) — шум.

### Локация

* `loc` — точное совпадение `search_location_id` и `item_location_id` (мягкий буст, не фильтр: совпадение есть
  только в 82% релевантных пар train);
* `geo` — `exp(-dist_km / tau)`, где расстояние считается от координат объявления до центроида локации запроса
  (медиана координат объявлений этой локации в train и корпусе). Это важно: у 17% запросов бенчмарка в корпусе
  нет ни одного объявления их локации.

### Пул кандидатов

Для каждого запроса: top-100 каждого канала глобально + top-100 каждого канала внутри локации запроса +
top-300 базовой смеси (с гео-бонусом и без). В среднем ~840 кандидатов. Для каждого кандидата сохраняются
**точные** скоры всех каналов, поэтому веса смеси подбираются покоординатным подъёмом за секунды без
пересчёта тяжёлой части.

### Финальная смесь

```
score = 1.5·bm + 10·e5 + 0.25·tc + 1.0·sp + 0.5·mc + 1.0·loc + 2.0·exp(-dist_km/500)
```

Вклад признаков (Recall@50 при обнулении одного признака, валидация по ключу, базовое значение 0.836):
без `bm` 0.744, без `geo` 0.761, без `loc` 0.803, без `e5` 0.818, без `sp` 0.824, без `mc` 0.826, без `tc` 0.835.

## Валидация

* `train` → удаление полных дублей (`search_*` + `item_id`: 48 533 строки в группах дублей, удаляется 30 619 —
  повторные клики) → 467 054 строки.
* `GroupShuffleSplit(test_size=0.1, random_state=42)`:
  * **по тексту** `search_query` — основной режим, тексты val не встречаются в train;
  * **по полной комбинации** `search_*` — часть текстов val встречается в train, как у 37% запросов бенчмарка.
    Метрика перевзвешивается так, чтобы доля знакомых текстов была 37%.
* Запрос = полная комбинация `search_*`; ground truth = все `item_id`, выбранные в val для неё.
* **Один инстанс на текст:** в бенчмарке все 2 452 текста уникальны, а в val популярные тексты размножены по
  локациям и фильтрам (31 673 инстанса на 7 453 текста), что перекашивает метрику в сторону частых запросов.
* Корпус для валидации — все объявления train (344 825), т.к. пересечение с `benchmark_items` — лишь 9.6%.

### Проверенные и отклонённые идеи

* **Жёсткие квоты по локации** (N кандидатов из своей локации + остальные глобально): не лучше аддитивного буста
  (+0.0005 при N=10, −0.03 при N=50).
* **Канал истории `hx` в скоринге:** даёт кандидатов в пул, но в смеси получает вес 0 — его сигнал покрыт e5 и BM25.
* **Категорийный буст:** `search_category` почти всегда 114 и совпадает с категорией объявления в 99.99% пар —
  сигнала нет. Используется микрокатегория, предсказанная по похожим запросам (`mc`).
* **Word2Vec (RusVectōrēs)** из ранних экспериментов заменён на e5: сильнее и не требует POS-тегирования.

### Ограничения

* Офлайн-метрика не равна ожидаемому скору на лидерборде: корпус валидации (344 825) больше и шумнее
  корпуса бенчмарка (189 212), в нём ~40% объявлений с повторяющимся заголовком в разных городах.
* Для запросов с более чем 50 релевантными объявлениями Recall@50 < 1 недостижим.
* Resource-ограничение: e5 кодирует короткий текст (64 токена). Полный текст с описанием на GTX 1650 кодировался
  бы ~5 часов; описания покрывает BM25.

## Внешние модели и библиотеки

* **intfloat/multilingual-e5-base** (MIT) — эмбеддинги запросов и объявлений; локальная копия в
  `artifacts/e5_baseline/multilingual-e5-base` (скачать: `huggingface-cli download intfloat/multilingual-e5-base`).
* **pymorphy2** + `pymorphy2-dicts-ru` — лемматизация.
* scikit-learn, scipy, numpy, pandas, pyarrow, PyTorch, sentence-transformers — версии зафиксированы в `uv.lock`.

## Воспроизведение

Данные: `dataset/train.parquet`, `dataset/benchmark_queries.parquet`, `dataset/benchmark_items.parquet`.

```bash
uv sync                                           # или: pip install -r requirements.txt && pip install -e .
uv run python -m avito_cg.run_val                 # валидация, сплит по тексту
uv run python -m avito_cg.run_val --split key     # валидация, сплит по ключу → artifacts/cache/weights_key_opt.json
uv run python -m avito_cg.run_bench               # answer.csv с весами из configs/weights.json
```

`run_bench` в конце проверяет формат: все `query_id`, ровно 2 колонки, ≤50 уникальных существующих `item_id`,
ID записаны строками в кавычках (ведущие нули не теряются). Пулы кэшируются в `artifacts/cache/pool_*.npz`;
после изменения каналов перезапускайте с `--rebuild` (кэш от других данных обнаруживается и отклоняется). Разделитель ID в колонке `answer` — запятая
(`--sep` меняет его).

Время на GTX 1650 / 16 ГБ RAM: кодирование e5 всех уникальных текстов объявлений (328 тыс.) — ~35 мин один раз
(кэш в `artifacts/cache/e5_text_cache`); индекс каналов — ~4 мин; пул на 2 452 запроса — ~2 мин.

## Следующий этап: ранжирование пула (CatBoost)

Кандидатогенерация оставляет запас: Recall@50 = 0.836, Recall@200 = 0.908, потолок пула (~840 кандидатов) = 0.944.
Линейная смесь не может вытащить в топ-50 то, что уже есть в пуле. План:

1. **Обучающие запросы.** Пул для отдельной выборки запросов из train_local (не из val), тот же сплит по тексту,
   чтобы не было утечки; таргет — объявление выбрано для этой комбинации `search_*`.
2. **Признаки кандидата:** сырые скоры всех каналов и их ранги внутри запроса, отрыв от лучшего кандидата, `loc`,
   расстояние, `mc`, `hx`; признаки объявления: цена (`item_price` → float, лог), рейтинг, число отзывов,
   скрытый телефон / запрет сообщений, длина описания, число дублей заголовка; признаки запроса: длина,
   наличие фильтров, «знакомый» ли текст.
3. **Модель:** `CatBoostRanker` (YetiRank / PairLogit) или классификатор с группами по запросу; оценка — Recall@50
   на той же валидации, сравнение с линейной смесью 0.836.
4. **Размер пула:** ранжировать top-200 по линейной смеси (0.908) или весь пул (0.944) — решить по времени обучения.
